- **Notes**: Two structural lessons worth pinning. (a) **`isConnected()` is "probably-connected" not "certified-connected" on iOS.** Reads `socket.conn?.readyState === OPEN`; iOS kills TCP at the OS level without flipping JS `readyState`; supabase-js's ~30s heartbeat is what eventually catches it. The first implementation used this signal as a wake-time health probe and skipped the rebuild on healthy. That produced a worse bug than the one being fixed — the banner appeared 30s later via heartbeat instead of immediately on wake. Lesson: don't optimize around an unreliable signal; the always-rebuild cost is ~50ms and the resulting channel is ground-truth fresh. Codified in `CLAUDE.md § Gotchas` → wake-recovery bullet. (b) **supabase-js reuses a single WebSocket across channel lifecycles.** `client.removeChannel()` + `.channel(...)` + `.subscribe()` does NOT trigger a new WS upgrade — channels piggyback on the existing socket. `page.routeWebSocket` intercepts upgrade requests, so it has no leverage on the rebuild path. This made the planned `broken-wake` E2E architecturally untestable; healthy-wake + the pre-existing `sync-error-banner` test (which intercepts the FIRST upgrade) is the testable contract. Lesson: for any test that wants to simulate "WS dies mid-session," routeWebSocket alone won't work without exposing supabase internals to `window` (test-pollution); rely on initial-upgrade interception + manual smoke for the wake-to-broken edge.

(a) **gotrue v2.188+ seed-compat regression unblocked Phase 3.** Phase 3 first-pass found 4 gates blocked on what looked like a local-Supabase auth-schema corruption (`auth.admin.listUsers` + password sign-in both returned 500 `Database error querying schema`). The subagent's hypothesis (Supabase CLI drift adding NOT NULL columns the seed didn't populate) was wrong. Empirical introspection via a direct postgres connection (`pg` package in /tmp scratch install, port 54322) showed all 35 `auth.users` columns were either nullable or defaulted. The actual root cause: gotrue v2.188+'s Pop ORM scans 4 text columns (`email_change`, `recovery_token`, `confirmation_token`, `email_change_token_new`) into Go `string` (not `*string` / `sql.NullString`), so SQL NULL trips a driver scan error on every read. gotrue's own signup path inserts `''` for these; the seed.sql `insert into auth.users` was missing the columns, so the columns took NULL by default. Fix: extend the seed's column list with `email_change, recovery_token, confirmation_token, email_change_token_new` set to `''` for the 2 seed users + add matching `auth.identities` rows (gotrue also expects every user to have at least one identity for the listUsers join). Verified with `pnpm db:reset` from a clean stack — auth admin + password sign-in both green. This fix shipped on the household-collaborators branch (commit `d54e975`) because it was tooling-blocker for THIS PR's pre-ship gates; co-locating it kept the build moving rather than splitting into a sibling cleanup PR. (b) **Supabase Realtime applies subscriber RLS to `postgres_changes` events** — empirically verified during fix-loop attempt 3. T13 (CRITICAL eng-review test added in `103be93`) was designed to validate D6/A4: owner removes member → next stale realtime event drives the channel teardown + redirect. The test failed on both mobile + desktop. Bonus finding: BROADCAST channels are NOT RLS-gated — a non-member can still receive broadcast events, which is a possible D6 v1 redesign path. **What this means for D6/A4**: the "realtime leak window" the design was meant to mitigate doesn't exist as designed for `postgres_changes`. The self-heal mechanism still works for the REST-triggered case (any user-initiated REST call → `fetchListEntries` returns null `currentHouseholdId` → throws → redirect). Coverage gap accepted for v0: a removed member with NO REST activity stays on stale UI until they navigate/refresh (already documented in spec § Success Criteria as "bounded to JWT TTL ~1h or next page mount/refresh"). T13 stays skipped (commit `a024206`) with the full finding in its body. Redesign path (server-side `member_removed` broadcast on a non-RLS channel) deferred to a follow-up PR. (c) **WebKit mobile + Playwright + controlled React inputs is a 4-attempt trap.** The rename E2E test on the mobile-webkit project failed 5 times before turning green: attempt 3 used `click('h1')` to blur (touch doesn't transfer focus to a non-interactive element); attempt 4 used `locator.blur()` (DOM blur event fires per trace, but React's synthetic onBlur doesn't observe it); attempt 5 used `press('Tab')` (key event fires per trace, still no React onBlur); attempt 6 used `pressSequentially` (per-character keydown/input/keyup) — green. Root cause: `fill()` on WebKit mobile dispatches the input event but doesn't propagate it into React's synthetic event system, so neither the debounce timer NOR the onBlur handler ever schedule a commit. `pressSequentially` fires real per-character keyboard events that React must observe. Codified pattern for future runs: prefer `pressSequentially` over `fill()` when the test depends on React's onChange firing through (debounce-save, controlled-input optimistic states). (d) **Pre-push adversarial reviewer sees only first 25 lines of PR body** — codified during Phase 4 by the /ship subagent: when the body's "ride-along infra commits" disclosure was at the BOTTOM, the reviewer failed it as "not disclosed" because the head-25-lines view didn't reach the disclosure. The subagent's argument was reasonable (4 blocked share one cause, environmental, CI re-runs the gates' content on a clean stack, prior PRs shipped similarly) but the /ak-build contract is explicit: `blocked > 0` halts. The "cheerful advance" failure mode the contract exists to prevent was avoided exactly as designed. (f) **Defensive scaffolding that checks the wrong condition is worse than no scaffolding.** D5's original spec called for a Sentry warning sentinel that fires when `NEXT_PUBLIC_SITE_URL` is unset AND `VERCEL_ENV === 'production'`. The intent was "warn the operator if they forgot to pin the canonical URL, so 7-day invite emails don't burn ephemeral preview URLs." But the actual failure mode (preview-URL-burns-into-7-day-email) happens when `VERCEL_ENV === 'preview'` — exactly the branch the sentinel explicitly skipped. So the sentinel fires on the harmless condition (prod, where `window.location.origin` already resolves to `lalista.store` correctly) and stays silent on the actually-problematic condition (preview signup that gets shared with a real user). User asked "why are we checking for it in the first place?" pre-merge; the answer was honest: the check is defensive scaffolding for a contrived scenario AND it instruments the wrong branch. Removed in commit immediately before merge — `resolveAuthSiteOrigin` keeps the `NEXT_PUBLIC_SITE_URL ?? window.location.origin` fallback (still useful as a canonical-URL pin), but the `maybeWarnOnMissingSiteUrl` function + global flag + warning tests deleted. Lesson: when adding defensive scaffolding from an outside-voice critique, verify the scaffolding ACTUALLY catches the failure mode it was added for.
