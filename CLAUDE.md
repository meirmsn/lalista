### Gotchas

Non-obvious rules surfaced by shipping work. Read before touching the relevant area. **Lalista-specific only.** Stack-wide patterns lifted to devshop guides where `/ak-implement` finds them via the routing index — see `/devshop/kit/docs/guide/README.md`.

- **`mark_item_bought` RPC is the ONLY way to mark bought**: RLS blocks direct client inserts to `purchase_history`. Use `markItemBought(client, entryId)` from `@lalista/core` which calls `supabase.rpc('mark_item_bought', { p_entry_id: entryId })`. Never call `purchase_history.insert` directly anywhere.
- **`list_entries.added_by` and `purchase_history.added_by` are nullable after migration 009** (`ON DELETE SET NULL` on the `auth.users` FK). UI must render an "added by someone" fallback everywhere it surfaces the author (see `ListRow.tsx`, `item/[id]/page.tsx`). `HydratedListEntry.addedBy` is typed `string | null`; always branch on null before showing a user identifier.
- **Information architecture (PR 3, D7; chapter 1l)**: `/` is a public landing for unauth visitors; authed users hitting `/` are redirected server-side to `/list` via `supabase.auth.getUser()` + `redirect()` inside `apps/web/app/page.tsx`. Middleware allow-lists `/`, `/sign-in`, `/sign-up`, `/forgot-password`, `/reset-password`, and `/auth/callback` for unauth pass-through; everything else still requires auth. The authed-on-public-path branch redirects authed users away from `/sign-in`, `/sign-up`, and `/forgot-password` (mid-session visits to those screens are a confused state) but NOT from `/reset-password` or `/auth/callback` (recovery flows arrive with a session already; the route handler creates the session). PWA `start_url` is `/list` so installed users skip the marketing screen on launch.
- **`fetchListEntries` returns `{entries, currentHouseholdId}`, not a bare array** (household-collaborators D6/A4). The wrapper probes `current_household_id()` (migration-001 helper) BEFORE issuing the list query. Why: when an owner removes a member, RLS on `list_entries` enforces "must be a household member" instantly on REST; but the removed user's Supabase Realtime channel keeps emitting until the JWT refreshes. Threading `currentHouseholdId` back to the caller lets `<ListClient>` self-heal: on every realtime event it debounce-refetches (1s); when the helper returns `null` the wrapper throws `RemovedFromHouseholdError`, the channel tears down via the existing `unsubscribe`, and the user is redirected to `/onboarding?removed=1`. Bounds the leak to ~1 round-trip. **How to apply**: every `fetchListEntries` caller must destructure `entries` from the result and catch `RemovedFromHouseholdError`. Do NOT "simplify" the wrapper back to a bare array — that would resurrect the leak.
- **Single-household v0 invariant lives in BOTH the application layer AND the DB layer; map 23505 in `OnboardingForm`** (household-collaborators D7/C2). `accept_invite` checks "already in a household" at the application layer (`P0001`), but the two-tab race surfaces at the Postgres `unique (user_id) constraint household_members_one_per_user_v0` (`23505`). The DB constraint is loud-over-silent — it's the structural backstop. **How to apply**: every API wrapper that calls a household-mutation RPC catches both `P0001 'already in a household'` AND `23505` with constraint-name match `household_members_one_per_user_v0`, mapping both to `InviteError 'already_in_household'`. `OnboardingForm`'s submit handler additionally bounces on the 23505: `if (err.code === '23505' && err.message.includes('household_members_one_per_user_v0')) { router.push('/list'); return; }` — the user auto-recovers to the household they just joined. **Do NOT use `23505` for application-layer "already in household" checks** — that errcode is reserved exclusively for the literal Postgres unique-violation from this constraint (D8).
- **Audit-feed display-name hydration is a two-query read, not a PostgREST join** (household-collaborators D13/C1). `household_audit_events.actor_user_id` and `target_user_id` both FK to `auth.users` (different schema); PostgREST relationship inference does NOT chain through `auth.*`. **How to apply**: `audit.ts` first selects audit rows, unions `actor_user_id` + `target_user_id` into a unique-ids set, then issues a second `profiles.select('user_id, display_name').in('user_id', uniqueIds)` call, then maps. When a user is deleted (`auth.users` deletion) or the profiles row is unreadable, both `actorName` and `targetName` are null and the UI renders `'someone'` (mirrors `addedByName`'s `'someone'` fallback in `ListRow.tsx`). The same pattern lives in `members.ts` for the household roster.
- **`subscribeToList` wake-recovery: always rebuild + suppress-window + pending-error tracking** (sync-banner-pwa-recovery D1–D8). iOS PWA / desktop-sleep resume can land the realtime channel in `CHANNEL_ERROR`/`TIMED_OUT` after the OS reaps the WebSocket while the tab is hidden — without recovery, the "Sync paused — tap to retry" banner appears every time the app returns to foreground, even on healthy resumes. `<ListClient>` binds one handler to three browser events (`visibilitychange` filtered to `document.visibilityState === 'visible'`, `online`, `focus`); on any wake it: (1) arms `suppressBannerUntilRef.current = Date.now() + SUPPRESS_WINDOW_MS` (3000ms ceiling), (2) resets `pendingErrorDuringSuppressRef.current = false`, (3) bumps `realtimeTick` to force a channel rebuild via the realtime `useEffect`, (4) refetches via `queueMicrotask`, (5) schedules a deferred banner-check `setTimeout(..., SUPPRESS_WINDOW_MS)`. Both `setSyncError({type:'realtime'})` sites in `ListClient.tsx` are guarded inside their existing `queueMicrotask` callback with `if (Date.now() < suppressBannerUntilRef.current) { pendingErrorDuringSuppressRef.current = true; return; }` — guard inside the microtask (not the listener body) so it reads a fresh `Date.now()` at the moment of intent-to-show, AND sets the pending bit instead of dropping the error so the deferred check can surface it at expiry. The suppress is cleared EARLY via `subscribeToList`'s `onSubscribed?: () => void` callback (5th arg, additive): when the rebuilt channel reports `'SUBSCRIBED'`, BOTH refs reset so subsequent errors surface normally and the deferred check no-ops. **Why always-rebuild, not probe-and-skip**: the original implementation probed channel health via `client.realtime.isConnected() && channel.state === 'joined'` and skipped the rebuild when healthy. But `isConnected()` reads `socket.conn?.readyState === OPEN`, which iOS lies about for ~30s after a TCP-level kill until the supabase-js heartbeat catches up — so the probe reported healthy on freshly-resumed PWAs whose WS was actually dead, the rebuild was skipped, and the banner surfaced 30s later via heartbeat. Always-rebuild is ~50ms of work and a fresh ground-truth channel; cheaper than the flicker. **Don't simplify**: removing the suppress would re-light the wake false-positive; removing the pending-error tracking would silently swallow CHANNEL_ERRORs that fire during the window (supabase-js doesn't auto-retry once it gives up); removing the deferred banner-check would let a genuinely-broken rebuild ship as a silent stale-data state. Bundled with this PR: `auth.onAuthStateChange((event) => { if (event === 'TOKEN_REFRESHED') void runFetch(); })` (D8) so JWT-refresh-driven visibility expansions (user removed mid-session and re-added) refetch under the new token. E2E coverage: `apps/web/e2e/realtime.spec.ts`'s `healthy-wake` + `broken-wake` cases.

- **Model B store visibility: globals visible to all authed users; customs visible only to the creating household** (my-stores D2). Migration 016 replaces the open `stores_select` policy with a scoped version: `is_global=true OR created_by_household_id ∈ (caller's households)`. All custom-store creation goes through `add_household_store` (SECURITY DEFINER) — there is no client INSERT/UPDATE/DELETE policy on `stores`. **The `add_household_store` RPC has TWO branches that both need a visibility check**: (a) the `p_name` fuzzy-match branch already restricts to visible rows via `where (is_global = true or created_by_household_id = v_household_id)`, and (b) the `p_store_id` direct-id branch — added during /ak-pre-ship Phase 3 of my-stores after the original migration shipped without it. Without (b), a caller who learned another household's custom store UUID (e.g. via an analytics dashboard leak) could call `add_household_store(p_store_id=<other>)` and the RPC would silently add that other household's custom store to caller's `household_stores`. SECURITY DEFINER bypasses RLS, so the RPC must enforce the visibility check itself. The integration test `case 2b` in `packages/core/src/migrations/016_household_stores.integration.test.ts` covers this. **How to apply**: don't add a redundant client policy on `stores` for INSERT — it would widen the surface; route through the RPC. Don't remove the `where … and (is_global = true or created_by_household_id = v_household_id)` clause from either RPC branch. **Why**: matches user mental model (global + private extras), avoids cross-household custom-name leak. Trade-off: catalog fragments over time (multiple "Trader Joe's" rows); operator-side admin-promotion is the dedup path (TODO `admin-promote-custom-store-to-global`).

- **BEFORE INSERT trigger on `list_entries` enforces `(household_id, store_id) ∈ household_stores` at the DB layer** (my-stores D4). Without this, a stale-tab client could write a `list_entries` row for a store the household just removed — RLS lets the insert through (membership check is on `household_id` only); the FK to `stores(id)` is open. **How to apply**: do NOT remove `check_list_entries_store_in_household_stores()` or its trigger. The 3-case integration test (allowed / blocked-by-removed / blocked-by-other-household-only) lives in `packages/core/src/migrations/016_household_stores.integration.test.ts` case 3. NOT applied to `purchase_history` (written via `mark_item_bought()` from already-validated `list_entries` rows), `brand_preferences`, or `disambiguation_log` (write-once-by-edge-function flows where this attack surface doesn't apply). Same fix-the-invariant-at-the-DB-layer pattern as 015's `FOR UPDATE` on `accept_invite`.

- **Edge-function routing-fallback membership gate lives INSIDE the silent_match conditional, not the asked_store else** (my-stores D5). At `supabase/functions/add-item/index.ts:388` (`if (routing.storeId && routing.confidence >= storeRoutingThreshold)`), the gate adds a `routedStoreInMyStores` check — on miss, the silent_match path is downgraded to `asked_store`. **How to apply**: do NOT move the gate into the `else` branch — that's already inside asked_store and the gate would never fire on the silent_match path the fallback exists to handle. The asked-store candidates query at lines 394-397 is rewritten to a `household_stores` join so only My Stores are offered. **Why service-role-but-`auth.uid()`-works**: the `supabase` client at `add-item/index.ts:72` uses service-role + forwards `Authorization` → RLS is bypassed (service-role) BUT `auth.uid()` resolves via the JWT → `current_household_id()` works correctly. Comment near the check makes this load-bearing.

- **`addHouseholdStore` returns `{storeId, wasCreated}` — `wasCreated=true` is the analytics signal for custom-store creation** (my-stores D11). The RPC returns the (single) row `(store_id, was_created)`; the API wrapper maps to the camelCase pair. Callers fire `my_store_added` (always) AND `custom_store_created` (only when `wasCreated=true`) per the PostHog count-of-rarer-events convention. **How to apply**: don't collapse the shape — `wasCreated` is the only client-visible signal that a new catalog row was minted. The strict-subset `custom_store_created` event is a deliberate PostHog query-cost optimization, not a duplicate.

- **`households` AFTER INSERT trigger auto-seeds `household_stores` with every is_global=true row** (my-stores D12, migration 017). The migration-016 cross-join backfill only seeds households that exist AT MIGRATION TIME — every new household created AFTER 016 ran (via `create_household_with_owner` RPC from migration 008, or any other path) would start with an empty `household_stores` and trip the BEFORE INSERT trigger (D4) with `store % is not in household %'s My Stores` on every `list_entries` insert. Migration 017's `households_auto_seed_my_stores` trigger closes the gap: AFTER INSERT on `households` → `seed_household_stores_on_new_household()` inserts every `is_global=true` row into the new household's `household_stores`. SECURITY DEFINER so it bypasses the (deliberate) absence of an INSERT policy on `household_stores`. **How to apply**: (a) any new code path that creates a `households` row inherits the auto-seed — don't manually duplicate the backfill in RPCs / admin tools / tests; (b) if a future migration changes the meaning of `is_global` (e.g., adds a region scope), update this trigger in lockstep; (c) the `on conflict do nothing` on the seed-insert is load-bearing for the case where a future code path pre-seeds rows before the trigger fires (defense-in-depth); (d) `AFTER INSERT` (not BEFORE) is load-bearing — the seed FKs to the new `households.id`, which must be visible. Coverage: `packages/core/src/migrations/016_household_stores.integration.test.ts` case 6.

- **Dropping a UNIQUE constraint? Audit `supabase/seed.sql` AND any cross-join backfill ordering in the same migration** (my-stores Phase 3 finding, 2026-05-11). A migration that drops a UNIQUE constraint (e.g. migration 016's `alter table stores drop constraint stores_name_key`) silently breaks every seed/migration site that referenced that constraint as an `on conflict (col)` target — Postgres raises `42P10 "no unique or exclusion constraint matching the ON CONFLICT specification"` and the seed run halts mid-way, leaving the DB in a partial state. **How to apply**: when dropping a UNIQUE, grep `supabase/seed.sql` + all migrations for `on conflict (<col>)` referencing the dropped column, and rewrite each site to either (a) `on conflict do nothing` if seed is the only writer for those rows, OR (b) `insert … select … where not exists (select 1 from <table> where <col> = v.<col>)` if the migration ALSO inserts overlapping rows (e.g. migration 001 inserts Costco/Walmart/Target + seed re-inserts them — pattern (b) dedupes correctly while (a) would accumulate duplicates). **Also audit cross-join backfill ordering**: if the same migration ships a cross-join backfill (`insert into X select from A cross join B …`) AND a seed inserts rows into A AFTER the migration runs, the backfill targets the migration-time empty A — those rows need a paired backfill in seed.sql (e.g. migration 016's `household_stores` cross-join targets zero households at migration-time; seed re-issues the same cross-join after inserting Alice + Bob). All three issues caught in a single Phase 3 because `pnpm db:reset` was the canonical surface that surfaced them. Defense-in-depth trigger (D4) firing during seed is the loud-fail signal — chase it back through this chain.

- **The web app deploys only from CI, as a Cloudflare Worker; never from a session.** CI's `deploy` job runs `scripts/deploy.sh` on push to `main` in the GitHub `production` environment (deployment branch rule: `main` only), which holds every production value: `CLOUDFLARE_API_TOKEN` (Workers Scripts Edit only), `CLOUDFLARE_ACCOUNT_ID`, `SUPABASE_PROD_URL`, `SUPABASE_PROD_ANON_KEY`, `SITE_URL`, and the Supabase/Sentry/Anthropic secrets. **How to apply**: never run `wrangler deploy`, `wrangler rollback` or `wrangler delete` from a session — rollback is the owner's call, using the undo line in the deploy summary. Every value the app reads is `NEXT_PUBLIC_*`, inlined at BUILD time, so a production value changes only with a new deploy; a new runtime (non-`NEXT_PUBLIC_`) env var would have to be set on the Worker, not just in GitHub. `wrangler.jsonc` holds no account id, routes or hosts, and `deploy.sh` refuses a config naming any Worker but `lalista` (a Workers token reaches every Worker in its account). No ISR, `next/image` or R2 cache: adding one needs an R2 bucket and a wider token, so it's a spec decision. Version pins: `@opennextjs/cloudflare` declares the Next versions it supports (`peerDependencies.next`); bump Next and OpenNext together and check the Worker in `pnpm preview:worker` (Next 16.3.8 and 16.4.1 fail `next/font/google` under Turbopack about one clean build in three, with "next/font/google queries have exactly one entry" — 16.4.2 doesn't, so after a Next bump build several times from a clean `.next` before trusting one green build; OpenNext 1.20.11 threw `Unexpected loadManifest(...preview-props.json)` on Next 16.4.1 — 1.20.12 fixed it).

### Testing

**E2E-per-surface invariant (PR 5).** Every user-observable surface has an E2E spec that exercises the primary action through the UI — not just an API-wrapper unit test. Concretely:

- For every page under `apps/web/app/**/page.tsx`, an E2E spec drives the primary verb (sign-in, add, edit, delete, sign-out). New page → new or extended spec in the same PR.
- For every API wrapper in `packages/core/src/api/*.ts`, either (a) a dedicated E2E spec exercises it through the UI, OR (b) the wrapper is transitively covered by an existing spec — cite the covering spec in the wrapper's JSDoc so the audit trail survives. Wrappers without either fail `/ak-test-review`.
- New PRs adding a UI surface or an API wrapper add a paired E2E in the same PR. Pre-ship `/ak-test-review` flags missing pairs; the future pre-commit test-presence hook (devshop, deferred) automates the check.
- Pattern reference: `apps/web/e2e/auth-edge-cases.spec.ts` for the admin-client + signup-per-test boilerplate; `apps/web/e2e/force-create-race.spec.ts` for two-context provisioning + DB-level assertions; `apps/web/e2e/realtime.spec.ts` for cross-session WebSocket coverage.

Unit tests live alongside their source (`packages/*/**.test.ts`); integration tests opt in via `VITEST_INTEGRATION=1`; E2E lives in `apps/web/e2e/`. Slow-job CI runs all three.

### Migration Workflow

```bash
supabase migration new <name>   # create migration (workspace — fs only, no docker)
pnpm db:reset                   # apply locally (relay → supabase-runner)
pnpm db:gen-types               # regen types from local stack (relay → supabase-runner)
# `supabase db push` (push to prod) is NOT run from the devcontainer —
```
