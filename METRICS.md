# Metrics

## Events

| Event                            | When it fires                                                                                                                                                                                                                                                                                                                                                                                                                                                  | Key properties                                                                                      | Why we care                                                                                                          |
| -------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------- |
| `auth_signed_in`                 | Successful session create for a returning user (fires from `onAuthStateChange` `SIGNED_IN`; brand-new accounts fire `auth_signed_up` instead, distinguished by `created_at` proximity).                                                                                                                                                                                                                                                                        | `method: 'email'`                                                                                   | Activation funnel — are returning users coming back without friction?                                                |
| `auth_signed_up`                 | First-ever `SIGNED_IN` for a new account (post-confirmation, when Supabase issues the session). Wired in `apps/web/app/providers.tsx`.                                                                                                                                                                                                                                                                                                                         | `method: 'email'`                                                                                   | Activation funnel — are new visitors crossing the sign-up → confirmation → session boundary?                         |
| `auth_signed_out`                | `signOut()` resolves successfully (settings page or programmatic).                                                                                                                                                                                                                                                                                                                                                                                             | `session_duration_seconds: number`                                                                  | Session length trend — signal for re-engagement friction.                                                            |
| `auth_password_reset_requested`  | `/forgot-password` form submit resolves successfully (regardless of whether the email is registered — no-enumeration). No PII properties.                                                                                                                                                                                                                                                                                                                      | `{}`                                                                                                | Forgot-password funnel entry — how often users ask for a reset.                                                      |
| `auth_password_reset_completed`  | `/reset-password` `updateUser({ password })` resolves successfully.                                                                                                                                                                                                                                                                                                                                                                                            | `{}`                                                                                                | Forgot-password funnel exit — how many requests turn into landed new passwords.                                      |
| `auth_email_confirmation_resent` | Resend click fires in `AwaitingConfirmationCard` (or any future legacy path).                                                                                                                                                                                                                                                                                                                                                                                  | `{ source: 'sign-up' \| 'sign-in-fallback' }`                                                       | Confirmation-mail deliverability signal — high resend rates suggest the first email isn't landing.                   |
| `item_added`                     | `invokeAddItem` resolves with `needs_followup === false` (item actually written to `list_entries`). Fired from the list view's add-item handler after the server confirms.                                                                                                                                                                                                                                                                                     | `{ store_id, was_disambiguated: boolean, was_force_created?: boolean, input_language: 'es'\|'en' }` | Core activation — are users adding items, and how often does NLP land silently vs. after a follow-up?                |
| `item_bought`                    | `markItemBought` resolves successfully. Fired from the list row's buy handler.                                                                                                                                                                                                                                                                                                                                                                                 | `{ time_on_list_seconds: number }` (derived from `added_at` → now)                                  | Habit loop closure — how long do items sit before being bought?                                                      |
| `disambiguation_shown`           | `invokeAddItem` resolves with `needs_followup === true`. Fired from the list view's add-item handler, same scope as `item_added`.                                                                                                                                                                                                                                                                                                                              | `{ candidate_count: number, followup_type: 'store'\|'item'\|'brand'\|'quantity' }`                  | Disambiguation rate — is the NLP + trigram stack doing its job or nagging users?                                     |
| `store_routed`                   | `invokeAddItem` resolves with a server-picked store (history-based routing; `needs_followup === false`). Fired client-side from the response payload before `item_added`.                                                                                                                                                                                                                                                                                      | `{ store_name: string, confidence_score: number }`                                                  | Store-routing quality — verifies >70% confidence routes land correctly in real life.                                 |
| `error_displayed`                | Sync error banner becomes visible. Three sources: (a) Realtime channel error, (b) list query network error, (c) Tier A2 optimistic-mutation retry budget exhausted (`useOptimisticMutation` failureMode `'banner'`, e.g. AddItem / Disambiguation). Deduped per error-instance — does not re-fire while the banner stays up. No new event added in chapter 1m — `error_type: 'sync'` extends the existing event's enum (D7 of `specs/app-snappiness/spec.md`). | `{ error_type: 'realtime' \| 'query' \| 'sync', screen: string }`                                   | Reliability signal — catch regressions in realtime stability, list-query stability, and add-item retry success rate. |
| `my_store_added`                 | `add_household_store` RPC resolves successfully (Settings → My Stores, AddItemSheet picker, or DisambiguationSheet store-followup branch). Fires once per successful add (idempotent re-adds still count as a user-intent signal).                                                                                                                                                                                                                             | `{ store_id, was_created: boolean, source: 'settings'\|'add_item'\|'disambig', household_id }`      | My Stores adoption — how often users curate per-household store membership; `was_created=true` splits to custom.     |
| `my_store_removed`               | `remove_household_store` RPC resolves successfully (Settings → My Stores only — no other remove surface in v0). Idempotent removal still fires.                                                                                                                                                                                                                                                                                                                | `{ store_id, source: 'settings', household_id }`                                                    | Churn signal on My Stores — pairs with `my_store_added` for net catalog growth per household.                        |
| `custom_store_created`           | `add_household_store` RPC resolves with `was_created=true` (custom-create branch — a new private catalog row was minted). Strict subset of `my_store_added`; emitted separately so the rarer-event PostHog query is cheaper than filtering `was_created=true` (D11).                                                                                                                                                                                           | `{ store_id, name, source: 'settings'\|'add_item'\|'disambig', household_id }`                      | Catalog gap signal — names users want that aren't in the global catalog (operator-side admin-promotion candidates).  |
| `store_routing_fallback_fired`   | Fires when the silent_match routing decision is downgraded to `asked_store` because the predicted store isn't in the caller's My Stores (D5). Detected server-side in `add-item` edge function (sets `store_routing_fallback_fired: true` on the response); fired client-side in `AddItemSheet.mutate` after receiving the flag — server-side PostHog firing deferred (no ingest key currently provisioned).                                                   | `{ removed_store_id, item_canonical, household_id }`                                                | Routing quality + My Stores curation correlation — how often household curation diverges from history.               |
